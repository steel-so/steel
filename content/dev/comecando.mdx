## Escolha a porta de entrada

O Steel recebe dados de outros sistemas por entradas próprias para integração.
Cada uma tem a sua forma de acesso, pensada para o caso de uso:

| Você quer | Entrada | Acesso |
| --- | --- | --- |
| Automatizar chamados, leads, oportunidades e templates em scripts, no CI ou no terminal | [API pública v1](/dev/api-v1) (`/api/v1/...`), pelo [Steel CLI](/dev/cli) ou pelo [SDK](/dev/sdk) | Token pessoal (`stl_pat_...`) no header `Authorization` |
| Receber no seu sistema o que acontece no Steel | [Webhooks que o Steel envia](/dev/webhooks#webhooks-que-o-steel-envia) | Assinatura `Steel-Signature` que você confere |
| Criar leads no CRM a partir do site, do ERP ou de uma automação | `POST /api/crm/integrations/leads` | Chave de API no header `Authorization` |
| Enviar um formulário do CRM pelo seu próprio front | `POST /api/crm/forms/<token>/submit` | Token público do formulário publicado |
| Iniciar um workflow do CRM a partir de um evento seu | `POST /api/crm/workflows/<token>/trigger` | Token do gatilho, na URL |
| Abrir (e encerrar) chamados no ServiceDesk a partir do seu sistema | `POST /api/servicedesk/monitoring/<token>` | Token da origem, na URL |
| Refletir issues e pull/merge requests nos chamados | `POST /api/integrations/github/webhook` e `POST /api/integrations/gitlab/webhook` | Assinatura do GitHub ou secret token do GitLab |

O restante da API (as rotas em `/api/workspaces/<id>/...`) é a que o próprio
aplicativo usa, exige a sessão de um usuário e pode mudar a cada versão. Para
automatizar, use a API v1. Veja [Autenticação e chaves](/dev/autenticacao).

Este guia mostra dois começos: [pelo terminal](#pelo-terminal-com-o-steel-cli),
com o Steel CLI e a API v1, e [pela chave de API do CRM](#crie-uma-chave-de-api),
para enviar leads de outro sistema. As outras entradas estão nos
[guias por caso de uso](/dev/guias/criar-lead).

## Pelo terminal, com o Steel CLI

O jeito mais rápido de chamar a API v1 é o [Steel CLI](/dev/cli). Ele faz o
login pelo navegador e guarda o token pessoal para você.

1. Instale (outros canais, inclusive Windows, em
   [Steel CLI](/dev/cli#instale)):

   ```bash
   brew install steel-so/tap/steel
   # ou: npm install -g @steel-so/cli
   ```

2. Entre. O terminal mostra um código e abre `/device` no navegador; confira o
   código, escolha o workspace, os módulos e o nível de acesso e clique em
   **Permitir acesso**:

   ```bash
   steel login
   ```

3. Confira quem está conectado e faça a primeira chamada:

   ```bash
   steel whoami
   steel api GET /me
   steel sd ticket list --assignee me
   ```

O `steel api GET /me` devolve o envelope da API v1:

```json
{
  "success": true,
  "statusCode": 200,
  "data": {
    "user": { "id": "ckv9x2p0h0000us7d3k1e5abc", "name": "Ana Souza", "email": "ana@empresa.com.br" },
    "workspace": { "id": "ckv9x2p0h0000ws7d3k1e5abc", "slug": "empresa", "name": "Empresa" },
    "role": "MEMBER",
    "scopes": ["api:read"],
    "modules": ["SERVICE_DESK", "CRM"],
    "token": { "id": "cm2tok...", "expiresAt": "2027-01-16T12:00:00.000Z" }
  }
}
```

A mesma chamada com `curl`, usando um token criado em **Configurações › Segurança ›
Tokens de API**:

```bash
curl "$STEEL_URL/api/v1/me" -H "Authorization: Bearer $STEEL_TOKEN"
```

E em TypeScript, com o [SDK](/dev/sdk):

```ts
import { createSteelClient } from '@steel-so/sdk'

const steel = createSteelClient({ baseUrl: process.env.STEEL_URL!, token: process.env.STEEL_TOKEN })
const me = await steel.me()
console.log(me.ok ? me.data.workspace.name : me.error.code)
```

Para usar no CI, sem navegador, veja [CLI em scripts e no CI](/dev/cli/scripts-e-ci).
Para os escopos, os módulos e a paginação, veja [API pública v1](/dev/api-v1).

## Crie uma chave de API

<Callout type='admin'>
  Só o **dono** ou um **administrador** do workspace cria e revoga chaves, e o
  módulo **CRM** precisa estar habilitado no workspace.
</Callout>

1. Entre no Steel, abra o **CRM** e clique em **Chaves de API**, no menu
   lateral, logo acima de **Configurações**.
2. Clique em **Nova chave** e dê um nome que diga quem vai usá-la (por exemplo,
   "Site institucional" ou "ERP").
3. Clique em **Criar chave** e copie o valor na hora. Ele começa com
   `crm_live_` e **não é mostrado de novo**: o Steel guarda só um hash.

Guarde a chave num cofre de segredos ou numa variável de ambiente do servidor
que vai chamar a API, nunca no código-fonte nem no navegador.

```bash
export STEEL_URL="https://homologacao.stratustelecom.com.br"
export STEEL_CRM_KEY="crm_live_..."
```

<Callout type='aviso'>
  Chame a API **do seu servidor**. A chave dá acesso de escrita ao CRM do
  workspace, e a API não libera chamadas de outros domínios pelo navegador
  (CORS).
</Callout>

## Faça a primeira requisição

O corpo precisa de um `name` e de **ao menos um e-mail ou telefone**. Os outros
campos são opcionais.

### cURL

```bash
curl -X POST "$STEEL_URL/api/crm/integrations/leads" \
  -H "Authorization: Bearer $STEEL_CRM_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Carlos Lima",
    "emails": ["carlos@empresa.com.br"],
    "phones": ["+5511999990000"],
    "company": "Empresa Exemplo Ltda",
    "source": "site"
  }'
```

### JavaScript (Node.js 18 ou mais novo)

```js
const response = await fetch(`${process.env.STEEL_URL}/api/crm/integrations/leads`, {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${process.env.STEEL_CRM_KEY}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    name: 'Carlos Lima',
    emails: ['carlos@empresa.com.br'],
    company: 'Empresa Exemplo Ltda',
    source: 'site',
  }),
})

const body = await response.json()
if (!body.success) {
  throw new Error(`${body.statusCode} ${body.error.code}: ${body.message ?? ''}`)
}
console.log(response.status === 201 ? 'Lead criado' : 'Lead já existia', body.data.id)
```

### Python

```python
import os
import requests

response = requests.post(
    f"{os.environ['STEEL_URL']}/api/crm/integrations/leads",
    headers={"Authorization": f"Bearer {os.environ['STEEL_CRM_KEY']}"},
    json={
        "name": "Carlos Lima",
        "emails": ["carlos@empresa.com.br"],
        "company": "Empresa Exemplo Ltda",
        "source": "site",
    },
    timeout=10,
)
body = response.json()
if not body["success"]:
    raise RuntimeError(f"{body['statusCode']} {body['error']['code']}")
print("Lead criado" if response.status_code == 201 else "Lead já existia", body["data"]["id"])
```

## Leia a resposta

Toda resposta vem no mesmo envelope. Um lead novo responde `201`:

```json
{
  "success": true,
  "statusCode": 201,
  "data": {
    "id": "ckx3lead0000ab7d3k1e5xyz",
    "name": "Carlos Lima",
    "emails": ["carlos@empresa.com.br"],
    "phones": [],
    "company": "Empresa Exemplo Ltda",
    "source": "site",
    "channel": "API",
    "stage": "RECEIVED",
    "score": 20,
    "ownerId": "ckx3user0000ab7d3k1e5abc",
    "createdAt": "2026-10-09T13:00:00.000Z"
  }
}
```

O exemplo está resumido: a referência de
[`POST /crm/integrations/leads`](/dev/api) lista todos os campos do lead.

- **`201`**: lead novo, já pontuado pelas regras de score e com dono pelas
  regras de roteamento.
- **`200`**: já existia um lead **em aberto** com o mesmo e-mail ou telefone. A
  API devolve esse lead e não cria outro, então reenviar a mesma requisição é
  seguro.

Se algo der errado, `success` vem `false` com um código estável em
`error.code`. Os mais comuns aqui:

| Status | Código | Causa |
| --- | --- | --- |
| `401` | `UNAUTHORIZED` | Header `Authorization` ausente ou sem `Bearer ` |
| `401` | `CRM_INTEGRATION_KEY_INVALID` | Chave errada ou revogada |
| `403` | `MODULE_DISABLED` | O CRM foi desabilitado no workspace da chave |
| `422` | `VALIDATION_ERROR` | Corpo inválido: sem `name`, sem e-mail nem telefone, e-mail malformado |
| `429` | `RATE_LIMITED` | Mais de 100 requisições por minuto com a mesma chave |
